# Architecture

How Arkuzo Memory Saver is put together, as of the working tree after v2.3.0 (engine `$ArkuzoRuntimeVersion = '2.3.0'`). It describes what the code does today, including the parts that are awkward. Line numbers refer to the files in `src/` and drift with every edit; function names are the stable reference.

## 1. Components and processes

```
ArkuzoMemorySaver.exe (launcher, .NET 10 single file)        exits after starting the Control Center
  │  installs/validates  app\versions\vX\ (4 files)  and  app\control-center\vX\ (6 files)
  ▼
pythonw.exe -I app\control-center\vX\Arkuzo-Control-Center.py --data <root>\data      (Control Center)
  │  ThreadingHTTPServer on 127.0.0.1:48650      serves Arkuzo-Control-Center.html to an Edge/Chrome --app window
  │  supervisor thread (2 s loop)                  starts, watches and restarts the engine
  ▼
powershell.exe -File app\control-center\vX\Arkuzo-Memory-Saver.ps1 -Headless -DataDirectory <root>\data   (engine)
  ├─ powershell.exe Arkuzo-Volt-Control.ps1   (Volt provider only: UI Automation adapter, one child per call)
  ├─ python Arkuzo-Volt-Probe.py              (Volt provider / conflict check: read-only SQLite probe)
  └─ RobloxPlayerBeta.exe ...                 (Arkuzo provider: the engine starts the clients itself)
```

| Component | Source | Runs as | Lifetime |
| --- | --- | --- | --- |
| Launcher | `src/launcher/Core/*.cs`, `App/Program.cs` | `ArkuzoMemorySaver.exe` | Seconds: update, validate, start the Control Center, exit. With `--console` (or no Python, or no add-on) it stays as the parent of a console engine. |
| Control Center | `src/saver/Arkuzo-Control-Center.py` (2,482 lines, standard library) | `pythonw.exe`, one process, several threads | Until the last window closes, **Quit**, or a newer version takes over. |
| Control Center page | `src/saver/Arkuzo-Control-Center.html`, generated by `build/bundle.ps1` from `src/saver/control-center/` (`00-head.html`, `01-styles.css`, `02-body.html`, `03-app.js`, `04-end.html`; four lines of the markup hold ~92 KB of embedded fonts and images). It ships as one file: the CSP only allows inline style and script, and the add-on ZIP holds exactly two files. | Browser app window | Polls `/api/state` every 2 s. |
| Engine ("saver") | `src/saver/Arkuzo-Memory-Saver.ps1` (about 6,500 lines, Windows PowerShell 5.1, six embedded C# types), generated by `build/bundle.ps1` from the 27 modules in `src/saver/engine/` (see 9) | `powershell.exe`, one thread plus a watchdog timer and short-lived worker tasks | Until `controller.stop` / `stop.signal`, `Q`, or a fatal error. |
| Volt adapter | `src/saver/Arkuzo-Volt-Control.ps1` (474 lines) | Child `powershell.exe` per call, 15 s limit | Volt provider only. |
| Volt probe | `src/saver/Arkuzo-Volt-Probe.py` (179 lines) | Child `python` per call, 3 s limit | Reads Volt's `state.db` read-only. |
| Executor signal script | `src/saver/00-arkuzo-signal.luau` (137 lines), embedded verbatim in the engine (`$script:ArkuzoAutoexecLuauContent`) | Inside the executor, in each client | Written to executor `autoexec` folders by `Sync-ArkuzoAutoexecSignals`. |

**Installed vs source.** The farm runs from `app\control-center\v<version>\`, which holds the two Control Center files plus verified copies of the four runtime files, because the Control Center starts the engine that sits next to it (`SAVER_SCRIPT = RUNTIME / 'Arkuzo-Memory-Saver.ps1'`). `Arkuzo-Control-Center.cmd` starts the Control Center from `src\saver` against the same `data\`. There is no supported way to run both: the port (48650), the controller mutex and the vault are shared, and a source copy with a higher engine version takes the installed one over (`take_over`).

**Account providers.** `accounts.provider` in `config.json` is `auto`, `arkuzo` or `volt` (`Resolve-ArkuzoAccountProvider`). With `arkuzo` the engine is the launcher and reads `data/accounts.json`; with `volt` Volt's account manager launches and the engine drives it through the adapter. Both produce the same "control status" object (`$voltControlStatus`), so the recovery core is shared. The variable and function names still say "Volt" for both.

## 2. Data contracts (files)

Everything lives in the data directory (`<root>\data`). Three files carry a schema version: `runtime-status.json` (`schemaVersion: 1`, a checked contract, see 2.3), `accounts.json` (`schemaVersion: 1`) and `recovery-state.json` (`schemaVersion: 2`); the readers of the last two do not check it.

| File | Writer | Readers | Notes |
| --- | --- | --- | --- |
| `config.json` | Control Center (`/api/config`, `/api/accounts/recovery`), launcher (first install only), engine (`Update-ArkuzoCookieSuspensions` appends to `recovery.excluded_account_ids`; first-run preset prompt) | Engine at start and every 10 s (`Update-ArkuzoLivePolicy`), Control Center | No shared lock between the two writers. Text compare decides whether to reload. |
| `accounts.json` (vault) | Control Center (`update_vault` → `save_vault`), engine (`Update-ArkuzoVaultAccount` → `Save-ArkuzoVaultFile`) | Both | Named mutex `Local\ArkuzoAccountVault`; cookies and link codes are `dpapi:<base64>` with entropy `Arkuzo.AccountVault.v1`. Flushed to the disk before the replace. |

| `vault-backups\accounts-<UTC yyyyMMdd-HH>.json` | Both vault writers, first save of each hour | Same as `.bak` | Newest 72 kept, plus the newest of each day of the last 7 (`vault_snapshots_to_remove` / `Get-ArkuzoVaultSnapshotsToRemove`, held equal by `VaultBackup.Tests.ps1`). |

### 2.1 `config.json`

Sections `settings`, `health`, `recovery`, `pagefile`, `accounts`, plus `selected_preset`, `config_lock`, `notes`. Shipped defaults: `config/defaults.json`. Reference: [configuration.md](configuration.md).

The rules, presets and vault settings have one source, `contracts/config-schema.json`. Validation still runs in three places: the Control Center (`SCHEMA`, `TOP_LEVEL`, `apply_config_changes`; its tables are generated from the schema by `build/bundle.ps1`), the engine (`Get-ArkuzoHealthPolicy`, `Get-ArkuzoRestorePolicy`, `Get-ArkuzoLiveResourceSettings`, `Get-ArkuzoPagefilePolicy`, written by hand) and the page (built from `GET /api/config`'s `schema`). `tests/saver/test_config_schema.py` holds the engine, the page's field tables and `config/defaults.json` to the schema. The `pagefile` section is engine-only and not in the schema. The engine keeps its last valid policy when a reload fails. `config_lock: true` clamps nine health values after validation, at start-up and again in `Update-ArkuzoLivePolicy`. `hard_limit` and `apply_graphics_flags` need an engine restart (`RESTART_KEYS`); everything else is applied live.

The engine's built-in fallbacks differ from the shipped defaults (for example `health.enabled` false vs true, `private_limit_mb` 4096 vs 6500, `startup_error_timeout_sec` 40 vs 5), so a `config.json` without a section behaves differently from a fresh install.

### 2.2 `accounts.json` (vault)

```
{ schemaVersion: 1,
  settings: { defaultPlaceId, launchDelaySec(5-120, 12), relaunchDelaySec(0-600, 8), launchTimeoutSec(30-600, 120),
              autoRelaunchEnabled, farmRunning, privateServerMode(none|shared|assigned), sharedPrivateServerId,
              multiInstance, launchMethod(direct|protocol), cookieCheckMinutes(0-1440, 60),
              arrangeWindows, arrangeLayout(auto|grid|cascade), arrangeOverflow(minimize|overlap), arrangePerRow, arrangeWidth, arrangeHeight, arrangeGap,
              arrangeCorner, arrangeMonitor, arrangeOrder(fixed|name|launch), arrangeMode(keep|once),
              arrangeVisibility(normal|background|minimized), arrangeRequestedAtMs,
              robloxVersion(auto|version-<16 hex>), robloxVersionFallback, robloxVersionsDir,
              robloxVersionFollow(''|latest|exploit:<weao id>), robloxFollowRestart, robloxProtocol },
  accounts: [ { id (GUID), userId (int), username, displayName, alias, group, notes,
                cookie ("dpapi:..."), cookieStatus (alive|dead|moderated|unknown), browserTrackerId (10-16 digits, unique),
                autoRelaunch, privateServerId, placeId, lastError?,
                lastCheckAtMs, lastLaunchAtMs, createdAtMs, updatedAtMs, launchRequestedAtMs, closeRequestedAtMs } ],
  privateServers: [ { id, name, placeId, linkCode ("dpapi:..."), createdAtMs } ],
  unreadable: [ rows that failed validation, kept verbatim ],
  trash: [ { batch (16 hex), deletedAtMs, account: { the full row, cookie still encrypted } } ] }
                deleted accounts held UNDO_SEC (10 s) for Undo, then purged (timer, next delete, next start);
                the engine reads `accounts` only and keeps unknown keys when it writes
```

- **Damage and restore.** A vault that is empty, all NUL, truncated, not JSON or not an object with an `accounts` list is damaged (`parse_vault_bytes`, `ConvertFrom-ArkuzoVaultText`). `load_vault` retries three times, then `restore_vault` takes the lock, re-checks, copies the damaged bytes to `accounts.json.damaged-<time>` and replaces the file with the exact bytes of `.bak`, else of the newest valid snapshot, then clears the copy's request stamps (`launchRequestedAtMs`, `closeRequestedAtMs`, `arrangeRequestedAtMs`) in one normal save so an old Close is not replayed; the event (`VAULT_RESTORED_FROM_BACKUP`) is queued for the activity feed (`take_vault_events`, drained by `App.step` and `vault_view`) and persisted to `control-center.log`. No valid copy: `VaultDamagedError`, nothing written; `vault_view` sets `damaged` and the page offers `POST /api/vault/reset` (`reset_vault`: refused while the file or any backup is valid). The engine never writes a damaged vault (`Read-ArkuzoVaultFile -Strict` in every read-modify-write); its other reads fall back, read-only, to the newest valid backup (`$script:vaultFallbackSource`, `VAULT_READ_FROM_BACKUP` once per source) and launches and the request stamps (`Invoke-ArkuzoNativeRequests`) are ignored meanwhile, because a rotated cookie could not be saved and the copy's stamps may be stale.
- The Control Center normalises on every write (`normalize_vault`): unknown fields on an account are dropped, malformed rows move to `unreadable`. The engine reads with `ConvertFrom-Json` and writes the whole document back with `ConvertTo-Json -Depth 12`. A field added on one side must be added to `normalize_vault` or it disappears on the next Control Center write.
- **Requests from the page to the engine travel through this file**: `launchRequestedAtMs`, `closeRequestedAtMs`, `settings.farmRunning`, `settings.arrangeRequestedAtMs`. The engine carries them out in `Invoke-ArkuzoNativeRequests` / `Update-ArkuzoWindowArrangement` (every 3 s) and clears the per-account stamps.
- Engine writes: rotated cookie (only if the stored one is unchanged), `cookieStatus` `dead` (401) or `moderated` (403 "User is moderated") at launch, `lastError`, `lastCheckAtMs`, `lastLaunchAtMs`, and the cleared request stamps.

### 2.3 `runtime-status.json` (heartbeat)

The heartbeat is a versioned contract: `contracts/runtime-status.json` lists `schemaVersion` (1), every top-level key, the keys of a `clients[]` row, an `accounts[]` row and `settings`, and which keys each reader relies on. `tests/saver/RuntimeStatusContract.Tests.ps1` checks that the engine writes exactly those keys; `tests/saver/test_contracts.py` checks that the Control Center, the page and the launcher read nothing else. Adding a key is compatible (add it to the contract); removing, renaming or redefining one needs a new `schemaVersion`. A heartbeat without `schemaVersion` (an older engine) is read as before; a higher one is read too and the Control Center shows a notice.

Top-level keys, as written by `Write-ArkuzoRuntimeStatus`:

| Key | Meaning |
| --- | --- |
| `schemaVersion`, `version`, `pid`, `startTicks`, `updatedUtc`, `uptimeSec`, `controller` (true), `monitorOnly` (false) | Contract version, identity and freshness. `version` is the engine version. |
| `clients[]` | One per tracked client: `pid`, `startTicks`, `cpuPercent`, `residentMB`, `privateMB`, `responding`, `windowPresent`, `launchError`, `state`, `sampleTime`, `eligible`, `isDisconnected`, `parentId`, `account`, `slot`, `ageSec`, `nextTrim`, `gameReady`, `disconnectReason`, `memoryPriority`. |
| `accounts[]` | `accountId`, `username`, `processId`, `uiStatus` (Connected, Launching, Idle, Unknown), `controlReady`, `cookieStatus`, `suspensionSafe`, `autoRelaunch`. |
| `expectedAccounts`, `missingAccounts`, `pendingRecoveries`, `missingRecoveryBlocked`, `suspendedAccountCount` | Counters. |
| `pending[]`, `quarantined[]`, `suspendedAccounts[]` | The journal's in-memory state (section 5). |
| `health`, `recovery`, `pagefilePolicy` | The validated policies in force. |
| `settings` | `mode`, `targetMB`, `trimEnabled`, `trimEverySec`, `effectiveTrimSec`, `trimPressure`, `availablePhysicalPercent`, `adaptiveTrim`, `priority`, `memoryPriority`, `coresPerInstance`, `softLimit`, `configLocked`. |
| `systemMemory`, `totalPhysicalMB`, `totals`, `trims` | Memory and totals. |
| `alerts[]` | `key`, `message`, `ageSec` (the throttled warnings of the last 30 s). |
| `robloxVersion` | Which Roblox build launches start (`Update-ArkuzoRobloxVersionStatus`): `mode` (auto/pinned), `pinned`, `fallback`, `selectedPath`, `selectedVersion`, `method`, `problem`, `managedRoot`, `checkedUtc`; `null` until the first check. Arkuzo provider only. |
| `voltControlAvailable`, `recoveryJournalHealthy`, `logFailed`, `accountProvider`, `accountProviderNotice`, `farmRunning`, `remoteSession`, `updateAvailable`, `pagefile`, `nativePrivileges`, `graphics` | Status blocks. |

Every `clients[]` row has the same 20 keys. Inside the engine a client's `LastSnapshot` is written by the full main-loop sample and patched in between by `Invoke-ArkuzoHealthObservation` with raw values, and it is partial until the first full sample; `ConvertTo-ArkuzoClientRecord` turns it into the heartbeat row: fixed keys, one rounding, `sampleTime` in UTC, identity (`startTicks`, `slot`, `parentId`) from the client's state, and `null` for what is not known yet. The diagnostic log still records the raw snapshot. `App.state` forwards the keys in `HEARTBEAT_VIEW_KEYS` to the page, so a new heartbeat key the page needs is added in the engine, the contract and that list.

Who relies on what: the supervisor needs `pid`, `startTicks`, `updatedUtc`; instant close needs `accountProvider`, `clients[].pid/startTicks`, `accounts[].accountId/processId`; the launcher's takeover needs `pid`, `startTicks`, `updatedUtc`, `controller`, `monitorOnly`.

### 2.4 `recovery-state.json` (journal)

`{ schemaVersion: 2, attempts[], launchAttempts[], pending[], suspendedAccounts: [], quarantined[], updatedUtc }`. `attempts` and `launchAttempts` are the UTC times of closures and launch requests in the last hour (the budgets survive a restart). A pending entry is `{accountId, oldTrackerId, oldPid, oldStartTicks, createdUtc, closedUtc, status, retryCount, nextRetryUtc, readySinceUtc, lastObservedUtc, replacementPid, replacementStartTicks, missingSinceUtc?, farmFreezeEpisode?}`. On load, readiness timers are cleared and entries without a verified old process are dropped; suspensions are never restored; quarantines are. A journal that fails to parse marks `recoveryJournalCorrupt` and blocks every destructive step until someone fixes or deletes the file.

### 2.5 Diagnostic log

JSON lines, one file per session part, rotated at `-MaxLogMB` (10 MB) keeping five parts **per session**. At start, `Invoke-ArkuzoLogRetention` deletes older sessions beyond the newest `-MaxLogSessions` (200) or `-MaxLogTotalMB` (300 MB), never the current one (the live folder had grown to 196 files, 536 MB). A failed write pauses logging for 5 s, then `Write-Diagnostic` opens a new part; `logFailed` means "the last write failed", not a session latch. Roughly 90 event names exist; the Control Center shows the ones in `EVENT_KINDS` (`summarize_event`). `WARNING` events carry the throttled dashboard notices (`Warn-Throttled`, one per key per 30 s). Error text that could hold a ticket or cookie is never logged: `Write-ArkuzoFailureDiagnostic` keeps type, HRESULT and line only.

## 3. HTTP API

`ThreadingHTTPServer(('127.0.0.1', port))`, default port 48650. Every request must carry `Host: 127.0.0.1:<port>` or `localhost:<port>` (DNS-rebinding guard). Responses set `Cache-Control: no-store`, `nosniff` and a CSP that only allows the page's own origin.

**What the token protects.** POST routes need `X-Arkuzo-Token` (or `token` in the body for the close beacon). GET routes need no token, and `GET /` returns the page with the token written into it (`const TOKEN = '...'`). So the token stops other web origins (CSRF); it does not stop another program running as the same Windows user, which can read it from `/`. `take_over` uses exactly that to stop an older Control Center.

| Method and path | Token | Body → result |
| --- | --- | --- |
| GET `/`, `/index.html` | no | The page, token substituted for `__ARKUZO_TOKEN__`. |
| GET `/api/ping` | no | `{app, version, instance}`; the launcher and `take_over` identify the Control Center by `app`. |
| GET `/api/state?since=&events=&page=&inst=` | no | Supervisor state, selected heartbeat keys, history, events, derived issues. Registers the page id as an open window. |
| GET `/api/vault` | no | Vault without cookies or link codes, joined with live status, monitors, screen size, sign-in state. |
| GET `/api/config` | no | `{config, presets, schema, restartKeys}`. |
| GET `/api/roblox?refresh=&cached=` | no | The Roblox tab: Roblox's current build, weao.gg's builds and exploit list (cached 5 min), installed builds, the selection, install progress. |
| GET `/api/avatar?userId=` | no | Cached PNG or 404. |
| POST `/api/saver/start`, `/stop`, `/restart` | yes | Supervisor action; `stop` can take 25 s. |
| POST `/api/trim-now` | yes | Writes `trim-now.signal`. |
| POST `/api/config` | yes | `{changes}` → validated merge, backup, write; returns `restartRequired`. |
| POST `/api/accounts/recovery` | yes | `{accountId, enabled}` → edits `recovery.excluded_account_ids`. |
| POST `/api/prefs` | yes | `autopilot`, `startSaverOnLaunch`, `startWithWindows` (HKCU Run key). |
| POST `/api/vault/add`, `/login`, `/login/cancel`, `/check`, `/update`, `/remove`, `/launch`, `/close`, `/settings`, `/arrange`, `/servers/add`, `/servers/remove`, `/reset` | yes | Vault actions (`vault_action`). `/reset` starts an empty vault when `accounts.json` is damaged and no valid backup exists (2.2). |
| POST `/api/vault/bulk` | yes | `{action, ids, value?, batch?}`: `delete` (held for Undo, answers `{batch, count, undoSec}`), `restore` (`batch`), `group` (`value` text, empty = remove), `relaunch` (`value` bool), `launch` (signed-out and moderated accounts skipped), `close` (exact clients only), `check`. Every id must exist or nothing changes; one locked, atomic vault write (`bulk_accounts`). |
| POST `/api/farm/start`, `/stop`, `/close-all` | yes | `farmRunning` and close stamps; `stop` and `close-all` also close mapped clients at once. |
| POST `/api/remote/leave`, `/api/remote/session` | yes | Hand an RDP session back to the console (`tscon`); session info. |
| POST `/api/window-closed` | body token | Close beacon from `pagehide`. |
| POST `/api/quit` | yes | `{stopSaver}` → optional saver stop, then shutdown. |
| POST `/api/roblox/install`, `/install/cancel`, `/remove`, `/select`, `/mode`, `/protocol`, `/exploits` | yes | Roblox tab actions (`ROBLOX_ROUTES`, behind `post_roblox`): `/mode` switches Auto / Newest / Exploit / Pinned (follow modes are re-checked every 10 min by `RobloxVersions.start_follower`), `/protocol` points `roblox-player:` (HKCU only) at the pin and restores it; [roblox-versions.md](roblox-versions.md). |

Errors: 400 `{error}` for `ConfigError`/`VaultError`, 403 for a bad host or token, 404, 413 above 256 KB, 500 for `OSError`. Any other exception is a 500 `{error: "Internal error (<type>)"}` (`Handler._guarded`; the type name only, never the message) and a line in the activity feed. Routes are a table: `GET_ROUTES` (path → `Handler` method, no token), `POST_ROUTES` (path → handler and its auth, `token` or `beacon`) and `VAULT_ROUTES` (the account and farm actions, behind `post_vault`). An unknown POST path needs the token before it is answered 404; an unknown `/api/vault/…` or `/api/farm/…` path is a 400 "Unknown account action". The page hard-codes the same paths; `test_control_center.py` checks that each of them has a route.

**Instant close** (`close_live_clients`): the Control Center terminates a `RobloxPlayerBeta.exe` itself when the heartbeat's provider is `arkuzo`, the account row names a pid, that pid appears in `clients[]` with a start time, and the live process has the same start time and image name. The close stamp stays set so the engine closes anything the heartbeat missed. The module docstring still says the Control Center never touches Roblox processes.

## 4. Engine main loop

One `while ($true)` at the end of the script (after `Draw-Dashboard`), single-threaded, sleeping `poll_ms` (350 ms by default) between passes. Start-up before the loop: take the controller mutex, start the stall watchdog, enable privileges, apply graphics flags, load the journal, resolve the provider, read control status, sync the executor script.

Per pass, in order (cadence in brackets):

1. `Process-ArkuzoExecutorSignals` — kick signals written by the executor script.
2. `Invoke-ArkuzoHealthObservation` — a 500 ms round-robin slice of cheap window/memory probes; it also runs before each client below and inside child-process waits, so health timers keep moving during slow IO.
3. Exit checks: `-RunForSec`, `controller.stop`, `stop.signal`.
4. `Update-ArkuzoLivePolicy`, `Resolve-ArkuzoAccountProvider`, `Update-ArkuzoLiveSettings`, `Sync-ArkuzoAutoexecSignals` [10 s].
5. `Get-ArkuzoSystemMemory` [5 s]; `Update-ArkuzoPagefileStatus` [30 s].
6. Volt: `Poll-ArkuzoVoltControlAsync`, `Update-VoltRecoveryCapability` + `Start-ArkuzoVoltControlStatusAsync` [15 s].
7. Arkuzo provider: `Get-ArkuzoNativeStatus` (vault read under the mutex plus one CIM query for command lines), `Invoke-ArkuzoNativeRequests`, `Update-ArkuzoWindowArrangement` [3 s].
8. Version check [30 min, in a background runspace]; trim plan; `trim-now.signal`.
9. `Get-Process RobloxPlayerBeta`; drop clients that are gone (`Record-ClientExit`, which may queue a relaunch).
10. **For each client:** first contact (one CIM query for parent, tracker id and build folder; retain a process handle as `Watcher`; nothing is read from or set on the process), then, once the client is `config_grace_sec` old and has a window or answered (`Test-ArkuzoClientConfigReady`, latched), capture the original priority, affinity, limits and memory priority and apply ours (`Invoke-ArkuzoClientConfiguration`, re-applied every 10 s; every step skipped for an exited client or one being closed, `Test-ArkuzoClientLive` / `Test-ArkuzoClientClosing`; the native calls go through one-line wrappers), minimise if asked, trim if due, CPU sample, find and tail the Roblox log, health sample and `Get-ArkuzoHealthDecision`, bind the account, build `LastSnapshot`.
11. `Complete-ArkuzoNativeLaunches` [every pass] starts the clients whose ticket request (a background runspace) has finished; `Update-ArkuzoRecoveryOutcomes` [`Get-ArkuzoOutcomeCheckDelay`: every pass while Arkuzo launches are queued, else 3 s; Volt 10 s] — the outcome state machine and the only place automatic launches start.
12. `Write-ArkuzoRuntimeStatus` [2 s].
13. `Update-ArkuzoRemoteSession` [2 s], `Update-ArkuzoKeepAwake`, `Update-ArkuzoFarmFreeze`.
14. `Invoke-ArkuzoRecoveryCandidates` — at most one budgeted closure per pass; with the Arkuzo provider every verified kicked client is closed in the same pass first.
15. `RESOURCE_SAMPLE` log record [`-LogEverySec`, 5 s], with `timings` (average and worst ms per pass for each loop phase, `Step-ArkuzoLoopPhase`); crash events and orphan crash-handler cleanup [15 s]; console dashboard [0.25 s, skipped with `-Headless`].

**Cost with many clients.** A healthy client costs two bounded `SendMessageTimeout` probes (a few ms), a log tail and a handful of process property reads per pass. An unresponsive client costs 100 ms per probe; it is probed once per pass, after its log IO (the observation slice re-probes a frozen client only when its last sample is 10 s old). The log search (`Find-RobloxProcessLog`) shares one listing of the Roblox log folder per pass (`Get-ArkuzoRobloxLogListing`) and reads each log head once, remembering its tracker id. The heartbeat serialises the whole state with `ConvertTo-Json -Depth 12` every 2 s. The code notes passes of 2–8 s on a farm deep in the pagefile; this is why health timers tolerate 30 s gaps and the supervisor waits 120 s before calling a hang.

**State.** The engine keeps its state in about 90 script-scope variables and one hashtable per client in `$tracked` (about 45 keys, some added lazily, such as `LogHeadRead`, `ArrangedStartTicks`). Functions read them freely, which is why tests have to dot-source every function and set script variables by hand. The recovery decisions are being moved off that state one at a time: `Get-ArkuzoControlledAccount`, `Test-ArkuzoSuspendedRowsSafe` and `Test-ArkuzoRecoveryHandoff` take an optional `-Context` (`New-ArkuzoDecisionContext`: now, restore policy, control status and when it was read, suspensions, pending recoveries, provider) and build it from the script state when it is left out; the launch gates have pure cores, `Test-ArkuzoLaunchSlotFree` and `Get-ArkuzoLaunchOrder`. `DecisionContext.Tests.ps1` calls them with hand-built contexts. Internal names that say "volt" for both providers (`$voltControlStatus`, `Update-VoltRecoveryCapability`) are unchanged, because tests set them by name; the context uses neutral names. Contract names (`voltControlAvailable`, config keys, routes, events, files) never change.

## 5. State machines

### 5.1 Client health (`Get-ArkuzoHealthDecision`, pure apart from its `$State` timers)

Evaluated on every sample; the first matching rule wins:

| Order | Condition | Reason | Closes after |
| --- | --- | --- | --- |
| 1 | commit ≥ 90% and private ≥ `pressure_min_private_mb` | `SYSTEM_COMMIT_PRESSURE` | at once |
| 2 | Volt startup notice on the window | `VOLT_STARTUP_ERROR` | `startup_error_timeout_sec` |
| 3 | disconnect or kick seen in the log or from the executor | `IN_GAME_DISCONNECT` | `disconnect_timeout_sec` |
| 4 | younger than `warmup_sec` | none (a latched farm-freeze member: `FARM_FREEZE`) | — |
| 5 | private ≥ `private_limit_mb` | `PRIVATE_COMMIT_LIMIT` | `private_limit_sustain_sec` |
| 6 | commit ≥ `pressure_percent` and private ≥ `pressure_min_private_mb` | `SYSTEM_COMMIT_PRESSURE` | at once |
| 7 | window present and not responding | `SUSTAINED_HANG`, or `FARM_FREEZE` for a latched member | `hang_timeout_sec` |

A gap of more than 30 s between samples resets the hang, freeze and memory timers. `Recycle` is only true when the sample is `eligible` (not monitor-only, health on, launcher capability present, client ownership proven).

### 5.2 Closure (`Invoke-ArkuzoRecoveryCandidates` → `Invoke-ClientRecovery`)

One closure per pass, largest private memory first (freeze members in onset order). Every gate must pass, in this order; a refusal costs nothing and is retried after 30 s:

1. Health and recovery enabled, controller mutex owned, journal healthy, farm running (Arkuzo), no remote hold (except commit pressure).
2. Fresh capability and control status (`Update-VoltRecoveryCapability -SyncControl`), ownership (`Test-ArkuzoClientOwnership`).
3. Exactly one account for this tracker id and pid, cookie alive, not suspended, not excluded (`Get-ArkuzoControlledAccount`); not quarantined.
4. **Handoff gate** (`Test-ArkuzoRecoveryHandoff`). Volt: no other account may have an open recovery, except a retry of the same account, a startup error that never reached a game, or a member of the active farm-freeze episode. Arkuzo: the client must map exactly (global mapping safe, its own tracker, same pid and start time); other accounts' open recoveries do not block it, because no account is ever quarantined.
5. Budget (`Test-ArkuzoRecoveryBudget`): `cooldown_sec` since the last closure (5 s for startup errors, `farm_freeze_spacing_sec` for freeze members) and `max_recycles_per_hour` (60) across all accounts. Arkuzo: a verified kicked/disconnected client (`Test-ArkuzoKickedClosure`) skips both and is not counted.
6. Identity by pid and start time on the retained handle, tracker id re-read from the command line (`Test-ArkuzoTargetRecovery`).
7. Journal the pending entry and the attempt, log `RECOVERY_REQUESTED`, then re-check everything that could have changed during that IO: the health reason, the account binding, the identity.
8. `Watcher.Kill()` on the retained handle, confirm exit within 2 s, set `closedUtc`, journal, log `CLIENT_CLOSED_FOR_RECOVERY`.

If anything fails after step 7 and the client is still the same live process, the reservation is rolled back. A failed log write blocks all of this until a later write succeeds (logging retries in a new part after 5 s).

Clients that exit by themselves while disconnected, frozen or due for recovery are queued the same way, already closed (`Register-ArkuzoExitedClientRecovery`).

### 5.3 Outcome and launch queue (`Update-ArkuzoRecoveryOutcomes`, `Get-ArkuzoOutcomeDecision`)

Runs over fresh, globally mapped control status (every pass while Arkuzo launches are queued, otherwise every 3 s, or 10 s with Volt). Entries are taken least recently tried first (`lastLaunchUtc`). First it adds missing accounts: with the Arkuzo provider every opted-in, alive account of a running farm without a client becomes a pending entry (`MISSING_ACCOUNT_DETECTED`); with Volt only when `restore_missing` is on and the account was launched before. Then, per pending entry:

```
              cancelled: farm stopped / excluded / not opted in / moderated / gone from inventory for restore_wait_sec
              quarantined (Volt only): retryCount >= abandon_after_retries, or age >= abandon_after_sec
 AwaitingReplacement ──► Wait ──► LaunchMissing ──► (client appears) Observing ──► Ready (entry removed)
        ▲                 │  not Idle, before nextRetryUtc,          │ healthy + in game + same process
        │                 │  or inside restore_wait_sec              │ for ready_stable_sec, samples <= 10 s old
        └── Blocked ◄─────┘  cookie not alive / mapping not exact    └─ any break resets readySinceUtc
```

- **Wait time before a launch.** Arkuzo: the vault's `relaunchDelaySec` (8 s). Volt: `restore_wait_sec` (90 s), because Volt relaunches by itself first.
- **Launch gates** (`LaunchMissing`): cookie alive and not suspended; no close request pending (Arkuzo); launch budget (Arkuzo: `launchDelaySec` spacing only, no hourly cap; Volt: `retry_base_sec` and `retry_max_per_hour`, shared by all accounts); commit below `pressure_percent`; no remote hold; a free launch slot (`Test-ArkuzoNativeLaunchSlot`, spaced from the engine's own launches and from clients it did not start / `Test-ArkuzoLaunchPacing`).
- **One launch per run**; with the Arkuzo provider the step runs on every pass while launches are queued, so `launchDelaySec` is the real spacing.
- **After a launch request**: `retryCount + 1`; `nextRetryUtc` is now + `launchTimeoutSec` for Arkuzo (fixed, no growth) and exponential `retry_base_sec … retry_max_sec` for Volt (`Get-ArkuzoRetryDelay`). Arkuzo: a refused ticket, no answer, or a client that closes before it is in game sets the retry to now + `relaunchDelaySec` instead (`Set-ArkuzoNativeLaunchRetry`, `Register-ArkuzoNativeLaunchExit`).
- **A launched client with no window after `launchTimeoutSec`** is closed (`NATIVE_LAUNCH_STALLED`, the client is flagged `Closing`) so the next run launches again.
- **Dead-build guard.** `Complete-ArkuzoNativeLaunch` records the build each launch starts (`$script:nativeLaunchBuilds`, direct launches and pins). A `NATIVE_LAUNCH_EXITED` of a client the engine did not close and that never reached the game counts against that build (`Register-ArkuzoRobloxBuildFailure`); 4 within 5 minutes mark it failing (`ROBLOX_BUILD_FAILING`), and `Resolve-ArkuzoRobloxPlayer` then refuses it (pinned without fallback, or Auto with nothing else installed: `blocked`, launches refused in the preflight before a ticket) or picks another build. A client of that build in game (`Register-ArkuzoRobloxBuildSuccess`, from the main loop) or another pin (`Sync-ArkuzoRobloxBuildGuardSelection`) clears it. Memory only. See [roblox-versions.md](roblox-versions.md).
- **Quarantine** (`quarantine_sec`, 30 min by default) applies to Volt only and survives restarts. The Arkuzo provider never quarantines; rows for vault accounts restored from an older journal are cleared.

`Invoke-ArkuzoNativeLaunch` (Arkuzo, step 1): read the vault under the mutex, refuse unless the cookie is alive, no close is requested, Volt is not running that account, the farm runs (or the launch is manual), no client and no launch in flight; build the join URL; start the auth-ticket request in a runspace (`Start-ArkuzoNativeTicketJob`: `Get-ArkuzoAuthTicket`, CSRF handshake, up to two 15 s requests, abandoned after 75 s with `BeginStop`). Step 2, `Complete-ArkuzoNativeLaunch` on a later pass: re-read the vault and re-check farm, close stamp, cookie and live clients; store a rotated cookie; 401 → `dead`, 403 "User is moderated" → `moderated`; resolve the Roblox build (`Resolve-ArkuzoRobloxPlayer`: Auto, or the pinned build, which step 1 already checked with `Get-ArkuzoRobloxVersionPreflight` so a missing pin never requests a ticket; a pin always launches directly) and apply graphics flags to a build installed after start-up; set aside a saved Roblox login (`Clear-ArkuzoRobloxSavedLogin`); start the client (`direct`: `RobloxPlayerBeta.exe --app -t <ticket> -j <url> -b <tracker>`; `protocol`: `roblox-player:` URI).

### 5.4 Account states

| State | Where | Entered | Left |
| --- | --- | --- | --- |
| `cookieStatus` alive / dead / moderated / unknown | vault | Control Center cookie check (`check_cookie`), engine at launch | Next check; re-adding the account. Dead and moderated accounts are never launched. |
| Suspended (dead cookie, idle) | engine memory only | `Update-ArkuzoCookieSuspensions` | Cookie alive again; the saved pending entry resumes. A suspended account that disappears from the inventory is added to `excluded_account_ids` in `config.json`. |
| Excluded | `config.json` | Per-account toggle, or the rule above | Toggle. |
| Quarantined | journal | Abandon rule in 5.3 | `untilUtc`. |
| Volt conflict | computed (`Get-ArkuzoVoltRelaunchConflict`) | Volt runs a client for that account | Client closed in Volt. |

### 5.5 Farm freeze (`Update-ArkuzoFarmFreeze`)

`Get-ArkuzoFarmFreezeCandidate` (pure) finds the largest group of frozen, low-CPU clients whose freezes began within `farm_freeze_onset_window_sec`; it needs `farm_freeze_min_clients` members that are a strict majority of the clients present, and is confirmed `farm_freeze_confirm_sec` after the last onset (`farm_freeze_remote_confirm_sec` right after a remote-desktop disconnect). `Start-ArkuzoFarmFreezeEpisode` latches the exactly mapped members (`Planned`) within the hourly budget. Members are then closed one at a time through 5.2, `farm_freeze_spacing_sec` after the previous member's exit; each ends as `Closed`, `Exited`, `Recovered` (answered again) or `Released`. The episode ends `Completed`, `Expired` (deadline) or `Disabled`. A second freeze within `farm_freeze_refreeze_sec` falls back to the normal hang timeout unless a new disconnect explains it. Episode state is in memory only. See [farm-freeze-recovery.md](farm-freeze-recovery.md).

### 5.6 Remote session

`Update-ArkuzoRemoteSession` [2 s] probes the WTS session, lock state, input desktop, display mode and Chrome Remote Desktop's connect/disconnect events (Application log, bookmark-based). A disconnected RDP session starts a **hold** on launches and closures for at most `remote_hold_max_sec`. A CRD disconnect only shortens farm-freeze confirmation. See [remote-desktop.md](remote-desktop.md).

### 5.7 Supervisor (`Supervisor.tick`, every 2 s)

States `stopped`, `starting`, `running`, `external` (a live engine it did not start), `restarting`, `crashed`.

- Fresh heartbeat (≤ 15 s) from its own child → `running`; failures reset after 10 min of uptime.
- Child exited → failure. Child silent for 120 s (after a 150 s start grace, and not right after the PC resumed) → kill, failure.
- Failure → restart after 5 s, then 10 s for every further failure (`restart_delay`, never growing). Eight failures in 30 min → crash loop: shown as such, retried every 15 s; every failure is logged.
- Operator stop → `controller.stop`, wait 25 s, kill; no restart until Start.
- Autopilot restarts a stopped engine; it also terminates an `external` engine whose heartbeat is older than 120 s.
- **Closing the last window stops the engine and quits** (`App.loop`, `window_close_due`, 8 s grace). A window that vanishes without its beacon leaves everything running.

### 5.8 Launcher (`LauncherEntry.Run`)

1. Take `Global\ArkuzoMemorySaver-<sha256 of root>`; if held, kill other `ArkuzoMemorySaver` processes and retry.
2. Ping the Control Center. If none answers and the controller mutex is held: `ControllerTakeover.Replace` (heartbeat → exact pid, start time, image and command line → stop file → kill by retained handle), then a fallback (`AutocloseRunningSaverProcesses` → `InstallProcesses.StopOwnEngines`): one CIM listing of `powershell.exe`/`pwsh.exe`, and a kill of each whose only `-File` is an `Arkuzo-Memory-Saver.ps1` inside this install's `app\` folder, re-checked by start time. Another install or a run from source is never matched. A held launcher mutex likewise only stops `ArkuzoMemorySaver.exe` processes whose image is in this install's folder (`InstallProcesses.StopOwnLaunchers`).
3. `Updater.PrepareAsync`: fetch `releases/latest` (30 s per request, 90 s in total), check names, sizes, URLs, SHA-256 and GitHub digests in memory, unpack with strict ZIP rules. Network errors fall back to the installed runtime. Newer → `Installation.Install`: stage folder → `Directory.Move` to `app\versions\vX`, seed `data\config.json` if missing, replace `app\current.json`, validate, then the same for `app\control-center\vX` and `app\control-center.json`. Downgrades are refused.
4. Start the Control Center with the first `pythonw.exe` on `PATH` that reports ≥ 3.8, and exit; otherwise run the console engine as a child.

An update records the version it replaces in `app\previous.json` (and `app\control-center.previous.json`), then removes every other version folder under `app\versions` and `app\control-center` (`PruneOldVersions`: current and previous are kept; folders whose name is not a version are left alone). `ArkuzoMemorySaver.exe --rollback` (refused while a Control Center or saver runs) checks the previous version's files, makes it current again, and writes the version it left to `app\skipped-version.json`; the updater does not install that release again, and the next newer release clears the skip. Older launchers ignore these files.

## 6. Threading, locking and atomic writes

| Lock | Kind | Held by | Purpose |
| --- | --- | --- | --- |
| `Local\ArkuzoSaver-ProcessController` | Named mutex, engine lifetime | Engine (not in `-MonitorOnly`) | One controller per session. Without it the engine refuses to start. The launcher only tests it. |
| `Local\ArkuzoAccountVault` | Named mutex, 10 s wait | Engine (`Invoke-ArkuzoVaultLocked`), Control Center (`vault_lock`) | Read-modify-write of `accounts.json`. Never held across a network request; both sides accept an abandoned mutex. |
| `Global\ArkuzoMemorySaver-<hash>` | Named mutex | Launcher | One launcher per install folder. |
| `ROBLOX_singletonMutex`, `ROBLOX_singletonEvent` | Named mutexes | Engine, Arkuzo provider (`Enable-ArkuzoMultiInstance`) | Lets several clients run. |

**Engine threads.** The loop is one thread. Besides it: the watchdog timer (`LoopWatchdogV1`, writes `saver-stall.json` when a phase is older than 60 s), one task per bounded log read (`BoundedReadV2`; a read stuck on a frozen client's log is abandoned after 2 s and that file is skipped until it returns), a runspace for the version check, and async stdout readers for child processes. Launch ticket requests run in a runspace per launch; vault IO, CIM queries and event-log reads run on the loop thread.

**Control Center threads.** One per HTTP request, the supervisor loop (daemon), a cookie-check worker, a browser sign-in worker, at most one Roblox install worker (`RobloxVersions`, cancellable). `Supervisor.lock`, `LogTail.lock`, `pages_lock` and `CookieChecker.lock` guard their own state; `config.json` writes from concurrent requests are not serialised.

**Atomic writes.**

- Engine: `Save-ArkuzoAtomicJson` → `Save-ArkuzoAtomicBytes` writes `<file>.<pid>.tmp` through a `FileStream` (`WriteThrough`, then `Flush($true)` = `FlushFileBuffers`, in `Write-ArkuzoDurableBytes`), then `File.Replace` (or `Move` when new), five attempts 60 ms apart. Used for the journal, vault, its backups and `config.json` (also the first-run `Save-ArkuzoConfigFile`). Only the heartbeat is written `-Volatile` (no flush): it is rewritten every 2 s and rebuilt after a restart.
- Control Center: `write_json_atomic` → `write_bytes_atomic` writes `<file>.<pid>.<thread>.tmp`, `flush` + `os.fsync`, then `os.replace`, five attempts on `PermissionError`. Every JSON it writes holds user state (vault, `config.json` and its backups, `control-center.json`, the Roblox protocol backup), so all are flushed.
- Why: NTFS journals the rename, not the data. A crash after the rename but before the lazy writer flushed the data left `accounts.json` as 28 KB of NUL (11 Nov).
- Launcher: `WritePointer` (temp + `File.Replace`), stage folder + `Directory.Move`.
- Readers retry: `read_json` three times 50 ms apart. A reader holding the file open is the usual reason a replace needs a retry.

## 7. Failure modes

| What fails | What happens | Recovery |
| --- | --- | --- |
| Engine exception outside a guarded block | `SAVER_FATAL_ERROR` (type and line only), settings restored, exit | Supervisor restart with backoff. |
| Engine loop blocked | Watchdog writes the phase; heartbeat goes stale | Supervisor kills it after 120 s of silence. |
| Diagnostic log write fails | `logFailed` is set; closures and crash-handler cleanup are refused while writes fail | Automatic: a new log part after 5 s. |
| Journal unreadable at start | `recoveryJournalCorrupt`: no closures, no outcome tracking | Fix or delete `recovery-state.json`. |
| Journal write fails | `recoveryJournalHealthy = false` until the next successful save | Next save. |
| Vault busy | Status `available = false`; no launches or closures | Next 3 s pass. |
| Vault damaged (crash during a save, bad edit) | Control Center restores `.bak` or the newest valid snapshot, keeps the damaged file, reports it; the engine reads the backup read-only and launches nothing until then | Automatic. Without any valid copy: nothing written; **Start a new account list** on the Accounts page. |
| Roblox build keeps closing at start | After 4 early exits within 5 min the build is not launched (`ROBLOX_BUILD_FAILING`); fallback or another installed build when allowed, else launches wait | A client of that build in game, or another build chosen. |
| Roblox unreachable or refusing tickets | Launch not started; Arkuzo retries after `relaunchDelaySec` at the normal spacing, forever (Volt: backoff and quarantine) | Automatic. |
| Cookie dead (401) | `cookieStatus = dead`, account suspended | Sign in again. |
| Account moderated | `cookieStatus = moderated`, pending entry dropped, never retried | A later cookie check finds it alive. |
| Saved Roblox app login | Moved aside before a launch (`RobloxCookies.dat.arkuzo-saved-login`) | — |
| Client never opens a window | Closed after `launchTimeoutSec`, relaunched | Automatic. |
| Pinned Roblox build missing | Launch refused before the ticket request (`ROBLOX_VERSION_PIN_MISSING`, dashboard warning), retried after the relaunch delay | Install the build on the Roblox tab, choose Auto, or turn on *Fall back if missing*. |
| Roblox install fails or is cancelled | Staging folder deleted; nothing reaches `Versions\` | Try again; a stale staging folder is deleted by the next install. |
| Frozen client holding its log | Read abandoned after 2 s, file skipped | Automatic. |
| RDP session disconnected | Hold for `remote_hold_max_sec` | Reconnect, or **Leave remote desktop**. |
| Commit pressure | Largest eligible client recycled; pagefile growth if allowed; launches wait | Automatic. |
| Control Center supervisor loop error | Every part of a pass is guarded (`App.loop`, `App.step`); the error type is shown as the supervisor message and the loop carries on | Automatic. |
| Control Center window closed | Engine stopped, Control Center quits; clients keep running unmanaged | Start it again. |
| Port 48650 taken or reserved | Control Center cannot listen (exit 1) | Free the port; `--port` exists but the launcher and takeover assume 48650. |
| GitHub unreachable at launch | Installed runtime validated and used | — |
| Release metadata or asset invalid | Launcher stops with an error, even when a valid runtime is installed | `--offline`. |
| Runtime folder has an extra or changed file | Validation fails; an in-place repair rewrites the files but does not remove extras | Delete the folder. |

## 9. Tests, build and release

- `build/test.ps1` runs each tracked `tests/saver/*.Tests.ps1` and `test_*.py` file in its own process, then `dotnet run` for the launcher harness. It carries on after a failure, prints a pass/fail summary and exits non-zero if anything failed. `-Filter <name>[,<name>]` runs a subset, `-List` shows the plan. Untracked test files are ignored in a git checkout. The whole suite takes several minutes.
- The PowerShell tests are plain scripts with their own `Assert`. Most parse the engine with the PowerShell AST, dot-source every function and stub `Write-Diagnostic`, `Warn-Throttled` and the IO they need; state is whatever script variables the test sets.
- Python tests load the Control Center by path and swap `HTTP['request']`. Servers listen on ports Windows hands out; one test starts a real headless Edge.
- `.github/workflows/tests.yml` runs the suite and the linters on `windows-latest` for pushes to `main` and pull requests.
- `build/lint.ps1` runs three linters: `build/lint-math.ps1` (ambiguous `[Math]::Min/Max` calls, which PowerShell binds to the Int32 overload and rounds; blocking, and also part of `build/test.ps1`), `ruff` with `ruff.toml` (real errors blocking, a wider rule set as a report) and PSScriptAnalyzer with `build/PSScriptAnalyzerSettings.psd1` (report only). A linter that is not installed is skipped with a note.
- `build/bundle.ps1` generates `src/saver/Arkuzo-Memory-Saver.ps1` (from `src/saver/engine/`), `src/saver/Arkuzo-Control-Center.html` (from `src/saver/control-center/`) and the schema blocks in `Arkuzo-Control-Center.py` (from `contracts/config-schema.json`), and stamps the version from `VERSION`. The generated files are checked in; `Bundle.Tests.ps1` and `bundle.ps1 -Check` fail when they are stale. `build/dev.ps1` runs the sources next to an installed copy. See [development.md](development.md).
- `build/package.ps1` checks the generated files (`bundle.ps1 -Check`) and copies them unchanged into the runtime ZIP (exactly four files) and the Control Center ZIP (exactly two), writes checksums, and rebuilds the launcher. `build/verify-release.py` checks a published release end to end with the real executable. The file lists are fixed in three places: `package.ps1`, `RuntimePackage.Files` / `ControlCenterFiles`, and `verify-release.py`. See [releasing.md](releasing.md).
